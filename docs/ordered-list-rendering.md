# 有序列表分页渲染修复

日期：2026-08-16

状态：已实现；本地门禁通过，远端状态以 `VERIFICATION.md` 为准

## 问题

折页使用 CSS 多列承载连续正文，再由每个 1080×1440 页面裁取对应列。浏览器原生有序列表的 `::marker` 位于列表内容盒之外；当列表落在新列左边界时，页面的 `overflow: hidden` 会裁掉序号左侧。

实际表现是正文仍然完整，但 `1.`、`2.` 等序号只剩右侧碎片。历史内容曾通过把列表改写为 `01｜…` 绕开问题，这不应继续成为作者负担。

## 故事卡 1：序号保持在安全画布内

作为使用 Markdown 有序列表的作者，我希望列表自动跨页后仍显示完整序号，从而不需要手写编号或针对单篇文章调整页面。

验收标准：

- 普通 `1–4` 与两位数 `9–12` 序号均完整显示。
- `<ol start>`、嵌套列表和自然换行继续使用浏览器语义。
- 无序列表和任务列表不因本修复改变。
- 单页预览与 1:1 导出共用同一条列表布局规则。

实现约束：

- 保留原生 `<ol>/<li>::marker`，只为有序列表预留足够的列内起始空间。
- 不把序号写回 Markdown，不引入自定义计数器或新的列表抽象。

## 故事卡 2：业务结果可自动验证

验收标准：

- 单元测试证明 Markdown 的有序属性与 `start` 值没有在解析阶段丢失。
- Chromium 测试把 `9–12` 列表强制放到第二页。
- 测试根据真实 `::marker` 宽度与分页裁切边界计算安全距离，要求序号左边界不越界；不以“某条 CSS 存在”代替业务断言。
- 测试确认分页画布仍为 1080×1440。

## 故事卡 3：最小质量门禁

验收标准：

- 提供 `lint`、`format:check`、`typecheck`、`test:e2e` 与统一 `check` 命令。
- GitHub Actions 在 pull request 与 `main` push 上执行依赖安装和统一检查。
- 浏览器测试运行在本地构建/预览服务上，匹配折页的实际交付方式；本项目不虚构云端部署流程。
- README 与验收记录写明真实命令、结果和未闭环边界。

## 变更边界

- 不拆分 `App.tsx`、`Preview.tsx` 或重写分页架构。
- 列表修复本身没有拆分 `App.tsx`、`Preview.tsx` 或重写分页架构。
- 后续质量收敛独立完成了全仓格式、recommended lint、语义拆包和 CI 门禁；没有把这些工作混进列表布局算法。

## 实现与复验结果

- `src/styles.css` 为 ordered list 使用 `padding-inline-start: 2.6em`，把原生 outside marker 的空间保留在列表内容盒内；没有改写 Markdown 或引入自定义计数器。
- `src/markdown.test.ts` 覆盖显式 `start=9` 的解析语义；当前单元测试为 6 个文件、22 项全部通过。
- `tests/e2e/ordered-list.spec.ts` 在生产构建的 Chromium 预览中把 `1–4` 和 `9–12` 放到第二页，按真实 marker 宽度验证 8 个序号不越过裁切边界，并验证 1080×1440 画布。
- `npm run check` 已在 2026-08-16 本机完整通过；`npm audit` 为 0 个已知漏洞。
- 实际 AI 工程技能地图文章稳定读回为 10 页、图片 7/7、控制台错误 0；第 1–3 页新截图使用 `*-fixed.png` 文件名保留了修复前证据。
- 后续质量收敛已把 formatter 扩至全部 31 个代码/配置/测试/脚本文件，启用 Biome recommended lint，并将生产 JS 拆成语义 chunk；构建会阻断任何超过 500 KiB 的 chunk。
